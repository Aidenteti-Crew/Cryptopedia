# 생태계 하위 페이지 API 연결 계획

## 목표와 범위

생태계 홈에서 이미 쓰는 크롤러 API를 체인·프로젝트, 매크로 소식, 행사·이벤트/아카이브, 개발 업데이트에도 연결한다. 수집 자료를 정적 예시 JSON으로 대체하지 않는다. 체인 기초·빌더 라이브러리·아카데미의 큐레이션 자료와 홈의 소개 문구는 유지한다. API·DB 스키마·수집기는 바꾸지 않는다.

## 데이터 흐름

| 화면 | 읽기 API | 화면 동작 |
|---|---|---|
| 체인·프로젝트 | `GET /api/ecosystem/projects?chain=...&limit=500` | 원본 카테고리와 검색 가능한 디렉터리, 프로젝트별 공식 링크 |
| 매크로 소식 | `GET /api/ecosystem/macro?chain=...&sort=latest&limit=100` | 최신 기사 목록, 원문 링크 |
| 행사·이벤트 | `GET /api/events?chain=...&status=<상태>&limit=100` (5개 상태 병렬 조회) | 오래된 지난 행사 때문에 예정 행사가 첫 페이지에서 밀리지 않도록 상태별로 조회·그룹 표시 |
| 행사 아카이브 | `GET /api/events?chain=...&status=past&limit=100` | 지난 행사 최신순 |
| 개발 업데이트 | `GET /api/ecosystem/updates?chain=...&sort=latest&limit=100` | 실제 기술 글 목록, 원문 링크 |

API 응답은 웹의 Zod 계약으로 검증한다. 목록이 비었으면 빈 상태를 표시하고, 오류가 나면 기존 다시 시도 화면을 표시한다. API가 주지 않는 프로젝트-개념 관계나 변경 영향 관계는 만들어 내지 않는다. 프로젝트와 기술 업데이트의 데모 목록은 생태계 메뉴에서 제외하되, 다른 학습 경로의 정적 자료는 유지한다.

## 단계

1. **계약과 공급자:** 실데이터 응답 타입·검증을 추가하고, `createCryptopediaRepository`의 네 페이지 조회 메서드를 API로 연결한다. 기존 정적 공급자는 큐레이션 화면과 그 테스트용으로 유지한다. 요청 URL, 체인 범위, 빈 결과, 오류를 테스트한다.
2. **화면:** `EditorialApp`의 분기를 실데이터로 바꾸고, 프로젝트 디렉터리와 기술 업데이트 목록을 API 필드에 맞춘다. 매크로·업데이트 기사는 원문 링크로 열고, 행사는 API의 상태·시간대·원문을 쓴다. 각 화면의 렌더 테스트를 먼저 작성한다.
3. **검증:** 로컬 API 계약과 웹 타입 검사를 실행한다. 기존 로컬 DB를 바꾸지 않고 별도 로컬 DB에 팀 dump를 복원할 수 있으면 4개 메뉴를 브라우저에서 확인한다. 기사와 행사 상태별로 100건까지 표시하며, 다음 페이지 UI는 후속 범위다.

## 완료 기준

- 네 메뉴와 행사 아카이브가 `/cryptopedia/{hub,macro,events,updates}.json`의 예시 목록을 표시하지 않는다.
- 체인을 바꾸면 각 API 요청의 `chain`도 바뀐다.
- 원문 링크가 있는 항목은 원문으로 이동하고, 없는 항목은 죽은 내부 상세 페이지를 열지 않는다.
- API 실패 시 정적 예시로 조용히 대체하지 않는다.
- 관련 테스트와 새 코드의 타입 검사가 통과하고, 브라우저에서 홈과 하위 메뉴의 자료 출처가 일치함을 확인한다.

## 2026-10-14 실행 결과

- 네 메뉴와 행사 아카이브를 API로 연결했다. 수집 기사 카드는 원문 링크를 열고, 프로젝트는 API의 카테고리별 디렉터리로 표시한다.
- 원본 `cherry_db`와 분리한 `cherry_avalanche_preview_20261014_v2`에 팀 dump를 복원했다. 매크로 26, 행사 18, 기술 업데이트 72, 프로젝트 235건을 확인했다.
- 브라우저에서 프로젝트 235건, 매크로 26건, 행사 18건(예정 2·지난 16), 업데이트 72건과 지난 행사 아카이브의 최신순을 확인했다. 코드 검토에서 발견된 행사 첫 100건 정렬 위험과 빈 아카이브 안내 누락은 상태별 조회·빈 상태 표시로 수정했다.
- 웹 관련 테스트 79개 통과, 수정 파일 ESLint 통과, `git diff --check` 통과. 웹 전체 타입 검사에는 기존 KaaS 파일 오류 8개만 남았고 이번 변경 파일의 오류는 없다.
- 로컬 검증은 API·웹의 4001·3002번 포트에서 수행했다. Dokploy 배포는 별도 수동 작업이다.
